# ドメイン用語集

MyHouseholdAccountBook（家計簿アプリ）で使われるドメイン用語をまとめたもの。

**位置づけ**：本書はコード・要件定義書から把握できる範囲で作成し、今後の機能追加のたびに追記・更新していく前提のドキュメントである（作成・更新の経緯は6章の更新履歴を参照）。網羅を目指すものではなく、既存の用語と新規機能の用語の対応関係が読み取れることを優先する。

---

## 1. 収支の基本概念

### 収支（しゅうし）
ユーザーの1か月分の収入・支出をまとめた集約。`INCOME_AND_EXPENDITURE_TABLE` に月単位（`TARGET_YEAR`/`TARGET_MONTH`）で1件保持する。収入金額・積立金取崩金額・支出予定金額・支出金額・収支金額（収入−支出）を持つ。

### 収入（しゅうにゅう）
月内に発生した収入の1件。`INCOME_TABLE` に保持する。給与などの通常収入のほか、「積立金取崩」（積立てていたお金を取り崩して収入として計上する）区分がある（収入区分 `INCOME_KUBUN`）。

### 支出（ししゅつ）
月内に発生した支出の1件。`EXPENDITURE_TABLE` に保持する。支出項目（後述）に必ず1件紐づき、支出区分（無駄遣いなし／無駄遣いB／無駄遣いC）を持つ。**実際の支払い行為の記録**である点が、後述の「買い物集計8項目」との違い。

**支出区分の導出規則（要件突合レビュー指摘W関連）**：`EXPENDITURE_TABLE`の行は支出区分を直接持つ専用カラムを持つが、固定費（`FIXED_COST_TABLE`）は同カラムを持たない。固定費由来の行の支出区分は、既存メソッド`ExpenditureCategory.from(FixedCostName)`（`domain/type/account/expenditure/ExpenditureCategory.java:94-102`。Feature1.03以前から存在）が**固定費名の文字列マッチ**（「無駄遣いC」を含めばWASTED_C、「無駄遣いB」を含めばWASTED_B、どちらも含まなければNON_WASTED）で導出する。固定費名を変更すると支出区分が変わりうる点に注意（dev1設計書5.4.1節の運用注意事項を参照）。

### 支出項目（ししゅつこうもく）
支出を分類するための階層マスタ。`SISYUTU_ITEM_TABLE` に保持し、レベル1〜5の親子階層を持つ（例：固定費(課税) > 積立金 > 旅行積立）。全ユーザー共通の初期セットは `SISYUTU_ITEM_BASE_TABLE`（管理者がアップロードするベースデータ）からユーザーごとにコピーされる。

### 支出金額（ししゅつきんがく）
月×支出項目単位で集計された金額。`SISYUTU_KINGAKU_TABLE` に保持し、支出予定金額・支出金額（実績）などを持つ。個々の「支出」レコードとは別に、月次の項目別集計値として管理される。

### 固定費（こていひ）
家賃・サブスクなど、毎月／隔月／任意月に発生する定額（または見込み）の支払いをあらかじめ登録しておくマスタ。`FIXED_COST_TABLE` に保持する。月初の収支登録時に、当月が支払月に該当する固定費が自動的に支出登録情報の初期値として展開される（`IncomeAndExpenditureInitUseCase`）。

### 収支登録
その月の収入・支出を確定登録する一連の画面操作。収入タブ・支出タブに分かれており、内部的には「収入登録」（`IncomeRegistUseCase`）と「支出登録」（`ExpenditureRegistUseCase`）に分割されている。最終的な登録確定処理は `IncomeAndExpenditureRegistConfirmUseCase` が担う。

## 2. 買い物登録まわり

### 買い物登録
日々の買い物実績を、店舗・カテゴリ別金額（食料品／外食／日用品／衣料品／仕事／住居設備など）で記録する操作。`SHOPPING_REGIST_TABLE` に1回の買い物ごとに1件保持する。現在は「簡易タイプ」（`SimpleShoppingRegist*`）のみが実装済みで、フル版（`ShoppingRegist*`）は未実装のスタブ。

### 店舗（てんぽ）
買い物先のマスタ。`SHOP_TABLE` に保持し、店舗区分（`SHOP_KUBUN_CODE`。食品・日用品店舗／ホームセンターなど）を持つ。

### 買い物集計8項目（かいものしゅうけい8こうもく）
買い物登録の日々の実績が自動的に集計・反映される、特定の8つの支出項目（食費・無駄遣いなし／食費・無駄遣いB／食費・無駄遣いC／日用消耗品／衣類・クリーニング・靴／住居設備／外食／仕事(流動経費)）を指す。この8項目に対応する `EXPENDITURE_TABLE` の行は、**個々の支払い行為ではなく複数の買い物の合算値**であり、通常の「支出」レコードとは性質が異なる（詳細は下記「集計レコードと実支払レコード」参照）。判定は支出項目コード＋支出区分（無駄遣い区分）の組み合わせで行う。実装は `ShoppingRegistExpenditureItemComponent` を参照。

**運用上の作成方法（Feature1.03-dev1で判明）**：この8項目は`IncomeAndExpenditureRegistConfirmUseCase`が自動生成するわけではなく、**ユーザーが固定費として固定費登録画面から登録しておく運用**である（例：`IncomeAndExpenditureInitIntegrationTest_FixedCost_202510_AllRequired.sql`参照）。毎月、既存の「固定費から収支を生成する」仕組み（`IncomeAndExpenditureInitUseCase.readInitInfo()`）により当月分がEXPENDITURE_TABLEへ展開される。`ShoppingRegistExpenditureItemComponent`はこの8項目が登録済みであることを**チェックするだけ**で、生成自体は行わない。買い物登録（`SimpleShoppingRegistUseCase`）は、既存のこれらの行を取得して金額を加減算する形で更新する（行が存在しない場合はエラー）。

**命名規約と一意性（Feature1.03-dev1の要件突合レビュー指摘S1・S2で確認）**：

- **命名規約**：8項目の固定費は、ユーザーが「この固定費の予定額はアプリが自動更新するため手動更新しない」ことを示す目印として、`FIXED_COST_NAME` に `【更新不可予定額(アプリ更新)】` を付ける運用になっている。この名称は収支登録処理で `EXPENDITURE_NAME` に引き継がれ、支出区分がB/Cの行にはさらに `【無駄遣いB】`／`【無駄遣いC】` の接頭辞が付与される（例：固定費名 `食費：無駄遣いB【更新不可予定額(アプリ更新)】` → 支出名 `【無駄遣いB】食費：無駄遣いB【更新不可予定額(アプリ更新)】`）。
- **この文字列はコード上のいかなる判定にも使われていない**：dev1着手前のソースを `アプリ更新` / `更新不可予定額` でgrepして不検出を確認済み。8項目の判定はあくまで `(支出項目コード, 支出区分)` の組み合わせ（`ShoppingAggregateSpecification`）で行う。なお `SISYUTU_ITEM_NAME` は `VARCHAR(15)` であり16文字の当該文字列は格納できないため、「支出項目名に付いている」という理解は誤りである。
- **混同注意**：文字列依存が存在しないのは `【更新不可予定額(アプリ更新)】` についてのみである。支出区分そのものの導出に使う `無駄遣いB` / `無駄遣いC` への依存は実在する（下記「支出」の節・`ExpenditureCategory.from(FixedCostName)` を参照）。
- **一意性**：8項目の重複登録はアプリ側が登録時に例外として弾くため、`(支出項目コード, 支出区分)` の組み合わせは実質的に一意である。ただし `EXPENDITURE_TABLE` のPKは `(USER_ID, TARGET_YEAR, TARGET_MONTH, EXPENDITURE_CODE)` であり、**DB制約としての一意性は担保されていない**点に注意（dev1のデータ移行では、この前提が成り立つことを件数検証で確認する方針とした。dev1設計書6.1節ステップ2）。

### 集計レコードと実支払レコード
`EXPENDITURE_TABLE` に混在する、性質の異なる2種類のレコードを区別する呼び方。

| レコード種別 | 性質 | 支払方法という属性 |
|---|---|---|
| 実支払レコード | 実際の1回の支払い行為の記録（固定費由来など） | 必須属性として意味を持つ |
| 買い物集計8項目（集計レコード） | 複数の買い物実績の集計値（導出データ） | 属性として適用対象外 |

Feature1.03-dev1で支払方法を必須項目として導入した際、この2種類の混在が課題として表面化した（後述「システム予約値」参照）。dev5でこの根本構造を見直す予定。

## 3. マスタ管理の共通パターン

### 表示順（ひょうじじゅん）
一覧・選択肢の並び順をユーザーが指定できる項目。店舗マスタ（`SHOP_SORT`）が原型で、以降の新規マスタ（銀行口座・支払方法など）もこのUI・運用パターンを踏襲する。登録・更新時に他データの表示順を自動でずらす「表示順シフト」ロジックが伴う（`ShopInfoManageUseCase` 参照）。

### 削除しない運用（無効フラグ方式）
他テーブルから参照される基準データ（店舗・支払方法・銀行口座など）は物理削除を行わず、「有効/無効フラグ」で一覧非表示・選択不可にする方式を取る。既存の登録済みデータ（固定費・支出など）が参照するマスタ行を消してしまうと過去データの整合性が壊れるため。

### システム予約値
ユーザーが編集・削除できない、アプリが業務上必要とする固定のマスタ行。以下の2つの実装パターンが存在する。

| パターン | 実装方法 | 例 |
|---|---|---|
| 明示的フラグ方式 | `ENABLE_UPDATE_FLG`（更新可否フラグ）カラムを持ち、`false`の行は更新処理を制限する | `SISYUTU_ITEM_TABLE`、Feature1.03-dev1の支払方法マスタ「支払方法がない」行 |
| コード帯予約方式 | 特定のコード範囲（例：990〜999）をシステム予約として扱う。値自体はマジックナンバーにせず、判定ロジックを1箇所（値オブジェクトの述語メソッドなど）に集約する | 店舗マスタの900番台、支払方法マスタのコード帯（990〜999、「支払方法がない」は999） |

「支払方法がない」は、買い物集計8項目（支払方法という属性が適用対象外のレコード）に対して、支払方法カラムをNOT NULLに保ちながら「該当なしの状態」を表現するための暫定的なシステム予約値である。dev5でこの8項目のデータ構造自体を見直した際に削除予定（[dev1設計指針](feature1.03/Feature1_03_dev1_支払方法固定値_設計指針.md)・[dev5設計指針](feature1.03/Feature1_03_dev5_集計8項目見直し_設計指針.md) 参照）。

**固定費登録画面のみの例外（要件突合レビュー指摘A・V対応）**：買い物集計8項目は固定費として登録する運用（上記「買い物集計8項目」参照）のため、「支払方法がない」の入力経路として固定費登録画面のみが正当である。他の画面（収支登録・買い物登録・店舗マスタのデフォルト支払方法選択など）の選択肢からは一律で除外するが、固定費登録画面の選択肢には含める。ただし無条件に許容するわけではなく、登録しようとしている固定費の支出項目コード・支出区分（固定費名から導出）が買い物集計8項目に一致するときのみサーバー側で許容し、一致しない場合はバリデーションエラーとする条件付きの扱いになっている。

### ENABLE_FLG と ENABLE_UPDATE_FLG の違い
似た名前だが意味が異なるため区別する。

| フラグ | 意味 | 操作主体 |
|---|---|---|
| `ENABLE_FLG`（有効/無効フラグ） | このマスタ行を選択肢・集計に使うかどうか | ユーザーが画面上でON/OFFを切り替える |
| `ENABLE_UPDATE_FLG`（更新可否フラグ） | このマスタ行をユーザーが編集できるかどうか | システムが固定（システム予約行のみ`false`） |

## 4. 支払方法・銀行口座（Feature1.03-dev1で新規導入）

### 支払方法（しはらいほうほう）
固定費・収支（支出側）・買い物登録で「何を使って支払ったか」を表すマスタ。`PAYMENT_METHOD_TABLE` に保持する。支払方法種別（下記）・銀行口座（種別により要否が異なる）・集計開始日（クレジットカードのみ）などを持つ。

### 支払方法種別
支払方法が5種類に分類される区分（`PAYMENT_METHOD_KUBUN`）。

| コード | 種別 | 銀行口座 | 備考 |
|---|---|---|---|
| 1 | 現金 | 不要 | |
| 2 | 口座振替 | 必須 | |
| 3 | クレジットカード | 必須 | 集計開始日（締め日）を持つ |
| 4 | デビットカード | 必須 | |
| 5 | 電子マネー（前払い式） | 不要 | 下記参照 |

### 銀行口座（ぎんこうこうざ）
支払方法が実際に引き落とされる（または現金の出所となる）口座のマスタ。`BANK_ACCOUNT_TABLE` に保持する。支払方法マスタから参照される。

### 集計開始日（しゅうけいかいしび）
クレジットカードの利用金額を締める起算日（1〜28。29〜31日を起算日とする実在のクレジットカードはないため対象外）。集計期間は「開始日 〜 翌月（開始日の前日）」として算出する（例：開始日=1 → 1日〜月末、開始日=15 → 15日〜翌月14日）。dev4（店舗・支払方法別買い物照会）の集計期間自動算出で使用する。

**基準月の表記について（要件突合レビュー指摘S対応）**：上記の例は要件定義書3.1と同じ「開始日を含む月を起点とした」表記に統一している。dev2（口座別支払確認・要件4.3）の文脈では「表示対象月において前回集計した期間」という**当月から見て前月にさかのぼる**言い方をすることがある（例：集計開始日=1のカードなら、表示対象月の前月分のクレカ利用合計）が、これは同じ期間の定義を別の基準月から言い換えているだけで、期間の算出ロジック自体（開始日〜翌月の前日）は同一である。dev2・dev4の実装時は、この2つの言い回しを混同しないよう注意する。

### 電子マネー（前払い式）
PayPay残高払い・イオン電子マネーなど、事前にチャージした残高から支払うキャッシュレス決済を表す支払方法種別。**チャージ金額・残高そのものは本アプリの管理対象外**とし、購入時点の支出のみを記録する（チャージと購入の両方を計上すると二重計上になるため）。

判別基準：
- 電子マネーの**残高から**支払った場合 → 支払方法種別「電子マネー（前払い式）」として登録する
- 電子マネーに**紐づけたクレジットカードから**支払った場合（例：PayPayのクレジットカード払い） → 実質クレジットカード払いのため、支払方法種別は「クレジットカード」として登録する（電子マネー種別としては登録しない）

後払い型電子マネー（PayPayあと払い等）も現時点では独立種別とせず「クレジットカード」種別に含めて扱う。将来チャージ・残高管理を導入する場合は、支払方法種別に属性を追加するのではなく「資産アカウント」を独立した集約として切り出し、チャージを支出ではなく資金移動としてモデリングする方針（詳細は [電子マネー対応の設計インプット](feature1.03/Feature1.03_dev1_payment-method-emoney-design-input.md) 参照）。

### 口座別支払確認（dev2予定）
支払方法マスタに登録した銀行口座単位で、その月の引き落とし予定額の合計を確認する画面（`AccountBookPaymentConfirmation.html`）。口座振替・クレジットカード・現金＋その他の内訳を表示する。

### クレジットカードポイント減算（dev2予定）
クレジットカードの利用代金のうち、ポイント利用分をあとから遡って減算登録する機能。買い物登録（簡易タイプ）でクレジットカード払いとして登録された明細のみが対象。

## 5. 積立金（dev3で本格導入予定）

### 積立金（つみたてきん）
支出項目マスタの「積立金」（`0033`）配下に、旅行積立・車検積立などの種類ごとに登録する支出項目。積立てる行為は支出として、取り崩す行為は収入区分「積立からの取崩し」として登録する。dev3で積立金種類ごとの残高管理機能（`TSUMITATE_BALANCE_TABLE`）を追加予定。

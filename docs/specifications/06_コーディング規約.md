# 06_コーディング規約

MyHouseholdAccountBookプロジェクト共通のコーディング規約です。別チャット・別セッションでの作業を含め、本プロジェクトに対応する場合は必ず本規約に従ってください。

## 1. Javaファイルヘッダの更新履歴

対象は **javaファイルのみ** です（その他のソースファイル・jsファイルは更新履歴を記載していないため対象外）。

### 1.1 記載フォーマット

ファイル先頭のブロックコメントに、以下の形式で更新履歴を記載します。

```java
/**
 * クラスの概要説明
 *
 *------------------------------------------------
 * 更新履歴
 * 日付       : version  ブランチ            コメントなど
 * 2026/05/27 : 1.00.00  feature-1.01-dev4   新規作成
 * 2026/08/18 : 1.01.00  feature-1.03-dev1   支払方法・銀行口座管理追加対応
 *
 */
```

### 1.2 各項目のルール

| 項目 | ルール |
|---|---|
| 日付 | ファイルの新規作成日付、および更新日付（`YYYY/MM/DD`） |
| version | 新規作成時は `1.00.00`。ブランチが変わるごとに中間桁を `1.00 → 1.01` のようにインクリメントし、末尾桁は `00` にリセットする。同一ブランチ内で複数回修正する場合は中間桁は変えず、末尾桁を `1.01.00 → 1.01.01 → 1.01.02` のようにインクリメントする。ブランチが `feature-2.00.**` のようにメジャーが変わったらversionも `2.00.00` に変わる。中間桁が99までカウントした場合は英字を利用する（例: `1.9A.00`） |
| ブランチ | 更新時点の現在のブランチ名を記載する |
| コメントなど | 新規作成時は「新規作成」、修正時はそのブランチでの修正対応内容を記載する |

### 1.3 区切り文字の注意

- 「日付」と「version」の間のみ半角コロン `:` の前後にスペースを入れて区切る（` : `）
- 「version」「ブランチ」「コメントなど」の間はスペースで桁を揃える（半角コロンは使わない）

### 1.4 追記時のルール

- 既存クラスを修正した場合は、1行目のブロックコメントに新しい行を **追加** する（既存行は変更しない）
- 同一ブランチ内で複数回同じクラスを修正した場合も、都度新しい行を追加する（1行に上書き統合はしない）。versionは中間桁を変えず末尾桁を1ずつインクリメントする（例: `1.01.00` → `1.01.01` → `1.01.02`）
- 同一ブランチ内で目的が同じ複数の修正を行った場合は、日付が異なっていても行を分けず1行にまとめてよい（例: 「UseCase結合テスト対応で@Getterを追加」といった同一目的の修正）。まとめる場合、日付は最新の修正日付に更新する

## 2. クラスjavadocの `@since` タグ

```java
/**
 *<pre>
 * クラスの説明
 *
 *</pre>
 *
 * @author ：Kouki Yonetani
 * @since 家計簿アプリ(1.03)
 *
 */
```

- `@since 家計簿アプリ(X.XX)` の `X.XX` 部分には、**そのクラスを新規作成した時点のブランチ** のバージョン部分を記載する
- 例: `feature-1.03-dev1` で新規作成したクラスは `@since 家計簿アプリ(1.03)`
- 一度記載した `@since` は、そのクラスが存在する限り新規作成時のブランチバージョンのまま変更しない（修正履歴の反映先は1.のヘッダ更新履歴のみ）

## 3. ファイルエンコード・改行コード

新規作成・更新するすべてのソースファイルは、以下の設定に統一します。

| 種別 | ファイルエンコード | 改行コード |
|---|---|---|
| java | UTF-8 | CRLF |
| sql | UTF-8 | LF |
| css | UTF-8 | LF |
| js | UTF-8 | LF |
| html | UTF-8 | CRLF |

- エディタ・IDE（Eclipse等）側の新規ファイルテンプレート・保存設定をこの表に合わせておくこと
- 既存ファイルを編集する際、対象ファイルのエンコード・改行コードが上記と異なる場合は、編集の混入によって意図せず設定が変わらないよう注意する（機械的な一括変換は本規約制定時点では未実施であり、別途対応するまでは既存ファイルごとの現状を尊重する）

## 4. インデント・ブレーススタイル

既存ソース（`application/usecase`配下、およびそれらが参照する`domain`・`presentation/controller`・`infrastructure`配下）の実装から抽出した規約です。

- **インデントは半角スペースではなくタブを使用する**
- 開き波括弧は行末に置く（K&Rスタイル。改行して新しい行に置かない）
- `if`・`for`・`while`等の制御構文は、キーワードと `(` の間にスペースを入れない

```java
if(条件式) {
    // 処理
} else if(条件式) {
    // 処理
} else {
    // 処理
}
```

## 5. Javadocコメントの記載スタイル

```java
/**
 *<pre>
 * メソッド（クラス）の概要説明
 *
 * 補足説明（必要な場合）
 *</pre>
 * @param 引数名 引数の説明
 * @return 戻り値の説明
 *
 */
```

- 説明文は `<pre>` ～ `</pre>` で囲む
- クラスjavadocの作成者タグは `@author ：Kouki Yonetani` の形式とする（`@author` と氏名の間は全角コロン `：` ＋前後スペースなし）

## 6. importの記載順序

以下の順にグループ化し、グループ間に空行を1行入れる。

1. `java.*` / `javax.*`
2. `org.springframework.*` 等のフレームワーク・ライブラリ
3. 自プロジェクト（`com.yonetani.webapp.accountbook.*`）。`application` → `common` → `domain` → `presentation` の順を目安とする
4. `lombok.*`

各グループ内はアルファベット順に並べる。

## 7. フィールド宣言のコメント

クラスのフィールド（インスタンス変数）を宣言する際は、直前の行に日本語の一行コメントでその役割を記載する。

```java
// 固定費テーブル:FIXED_COST_TABLEリポジトリー
private final FixedCostTableRepository fixedCostRepository;
```

## 8. ドメインモデルのファクトリメソッド（from）の型安全性

### 8.1 引数は値オブジェクト型にする（プリミティブ型のオブセッションを避ける）

ドメインモデルの静的ファクトリメソッド `from()` の引数は、`String` / `BigDecimal` / `LocalDate` / `boolean` 等のプリミティブ型ではなく、各項目に対応する値オブジェクト型（`UserId` / `ExpenditureAmount` 等）を受け取る形にする。

- プリミティブ型の引数が並ぶと、引数の順序を取り違えてもコンパイラが検出できない（同じ `String` 型が並ぶため）
- 値オブジェクト型にすることで、引数の取り違えがコンパイルエラーとして検出できるようになる
- プリミティブ値からの変換（`UserId.from(文字列)` 等のガード節を伴う生成）は、呼び出し元（UseCase・テストコードのヘルパー等）の境界で行う。`from()` 自体は値オブジェクトをそのまま私有コンストラクタへ渡すだけにする

```java
// Good: 値オブジェクト型を引数に取る
public static ExpenditureItem from(
        UserId userId,
        TargetYear targetYear,
        ExpenditureAmount expenditureAmount,
        ...) {
    return new ExpenditureItem(userId, targetYear, expenditureAmount, ...);
}
```

### 8.2 witherパターン（一部フィールドのみ変更した新しいインスタンス生成）で不要な再生成をしない

値オブジェクトは不変（イミュータブル）であり、生成後に値を変更する手段を持たない。そのため、一部フィールドだけを変更した新しいインスタンスを生成する場合（加算・減算等）、**変更しないフィールドは既存の値オブジェクトインスタンスをそのまま再利用する**。`.getValue()` でプリミティブに戻してから `XXX.from(...)` で再生成するのは無意味な複製であり行わない。

```java
// Bad: 変更しないフィールドまで不要に再生成している
public ExpenditureItem addSisyutuKingaku(ExpenditureAmount addValue) {
    return ExpenditureItem.from(
            UserId.from(userId.getValue()),
            TargetYear.from(targetYear.getValue()),
            ...
            ExpenditureAmount.from(expenditureAmount.add(addValue).getValue()),
            ...);
}

// Good: 変更しないフィールドはそのまま再利用し、変更対象のみ新しい値を渡す
public ExpenditureItem addSisyutuKingaku(ExpenditureAmount addValue) {
    return ExpenditureItem.from(
            userId,
            targetYear,
            ...
            expenditureAmount.add(addValue),
            ...);
}
```

- 値オブジェクトは不変なので、複数のインスタンス間で同じ参照を共有しても安全（防御的コピーが必要なのはミュータブルなオブジェクトを扱う場合のみ）
- 例外: 異なる値オブジェクト型への変換（例: `ExpenditureAmount` → `MinorWasteExpenditureAmount`）は正当な型変換であり対象外

### 8.3 テストコードでの対応（ヘルパーメソッド）

`from()` の引数を値オブジェクト型にすると、テストコードから直接プリミティブ値で呼び出せなくなる。この場合、各テストクラスに、プリミティブ引数を受け取り値オブジェクトへ変換してから `from()` を呼び出すprivateヘルパーメソッドを用意する（`FixedCostTest.helper()` 等を参照）。

```java
private FixedCost helper(String userId, String fixedCostCode, ..., BigDecimal fixedCostPaymentAmount) {
    return FixedCost.from(
            UserId.from(userId),
            FixedCostCode.from(fixedCostCode),
            ...
            FixedCostPaymentAmount.from(fixedCostPaymentAmount));
}
```

### 8.4 プレゼンテーション層（ResponseDTO）への適用について

8.1～8.3はドメインモデルの `from()` に関するルールであり、DDD（Evans/Vernon）が規定する値オブジェクトの原則そのものである。一方、プレゼンテーション層のResponseDTO（`getInstance()`/`from()`等）のファクトリメソッドにドメインVO型を引数に取らせる対応は、**DDDが要求する原則ではなく、本プロジェクト独自の設計判断（規約）** である。ResponseDTOはMVCの表示専用データホルダーであり、DDDの語彙（Entity/Value Object/Aggregate）には含まれないため、その生成方法自体にDDD上の正解・誤りはない。

本プロジェクトでは、以下の理由から、ResponseDTOのファクトリメソッドについてもドメインVO型を引数に取り、DTO内部で `.toFormatString()` / `.getValue()` 等による文字列変換を行う方式を採用する。

- 8.1と同じ理由で、同型プリミティブ引数の並びによる引数取り違えをコンパイル時に検出できる
- VO→表示文字列への変換ロジックを、UseCase側に分散させず、ResponseDTO（表示形式を知っている場所）に一元化できる

```java
// ResponseDTOのファクトリ：ドメインVOを受け取り、DTO内部で表示用文字列に変換する
public static ExpenditureRow from(ExpenditureCode expenditureCode, String displayName, PaymentDate paymentDay,
        ResolvedPaymentMethodName paymentMethodName, ExpenditureAmount expenditureAmount,
        ResolvedBankAccountName bankAccountName, ExpenditureDetailContext expenditureDetailContext) {
    return new ExpenditureRow(
            expenditureCode.getValue(),
            displayName,
            paymentDay.toDayString(),
            paymentMethodName.getValue(),
            expenditureAmount.toFormatString(),
            bankAccountName.getValue(),
            expenditureDetailContext.toFormatString());
}
```

**注意（型安全性とは別軸の観点）**: ResponseDTOのファクトリメソッド内で行ってよいのは「VO→表示文字列への変換（フォーマット）」のみであり、**業務計算（パーセンテージ算出等の派生値計算）をResponseDTO側で行ってはいけない**。計算はUseCase／ドメイン層の責務であり、ResponseDTOに渡す時点で計算済みの値（VOまたは計算結果）になっていることが望ましい。プレゼンテーション層への業務ロジックの染み出しは、型安全性対応とは独立した別の問題として都度チェックすること。

**判定基準は「呼び出し位置」ではなく「計算ロジックの実装場所」で見る。** ResponseDTOのファクトリメソッド内でドメインVOのメソッドを呼び出している場合、その呼び出し自体は問題ではない。確認すべきは、除算・四捨五入・条件分岐といった計算の実体コードがどこに書かれているかである。

- 計算の実体がドメイン層の値オブジェクト内に実装されており、ResponseDTO側はその結果を受け取るだけの呼び出しに留まっている場合 → **問題なし**（`.toFormatString()`と同じ「VOの振る舞いを呼ぶだけ」の扱い）
- 計算の実体（除算・四捨五入・条件分岐などの業務ロジック）がResponseDTOのファクトリメソッド内に直接書かれている場合 → **問題あり**（UseCase／ドメイン層に移すべき）

```java
// Good: 計算ロジックの実体はドメイン層のVOにあり、ResponseDTO側は呼び出すだけ
// MinorWasteExpenditureAmount（ドメイン層）
public String getPercentage(ExpenditureAmount expenditureAmount) {
    if(expenditureAmount == null) { throw ... }
    if(getValue() == null || ZERO.getValue().compareTo(getValue()) >= 0) { return ""; }
    BigDecimal pt = getValue().divide(expenditureAmount.getValue(), 2, RoundingMode.HALF_UP)...
    ...
}

// AccountMonthInquiryResponse（プレゼンテーション層）：計算はせず、VOの振る舞いを呼ぶだけ
sisyutuKingakuB.getPercentage(sisyutuKingaku)
```

実例: `AccountMonthInquiryResponse.ExpenditureListItem.form()`の`sisyutuKingakuB.getPercentage(sisyutuKingaku)`は、割合計算の実体が`MinorWasteExpenditureAmount`（ドメイン層）に実装済みであることを確認済みのため、問題なしと判断。

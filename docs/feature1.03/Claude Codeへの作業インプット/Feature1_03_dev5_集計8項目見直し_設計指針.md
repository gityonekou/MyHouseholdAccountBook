# dev5 設計指針: 支出8項目のデータ管理見直し

**対象**: `feature-1.03-dev5`
**位置づけ**: 要件定義書 7章 および 持ち越し事項No.6 の検討材料
**前提**: dev1完了（支払方法マスタにシステム予約値 `999` が存在する状態）

> **【dev1突合レビュー反映済み・`Feature1_03_dev5_設計指針_dev1突合レビュー.md`】** 本文書はdev1着手前に書かれたものだったが、dev1の調査・設計過程で判明した事実（8項目の実際の生成経路が固定費登録経由であること等）を反映済み（指摘D5-1〜D5-7）。着手時はこの反映内容を前提にしてよい。

## 1. 本devが解決すべき本質的な課題

### 1.1 表面的な課題

dev1で暫定的に追加した「支払方法がない」固定値（`999`）を削除する。

### 1.2 根本的な課題

`999` の存在は症状であって原因ではない。根本原因は、**支出テーブルに性質の異なる2種類のレコードが混在していること**にある。

| レコード種別 | 性質 | 支払方法 |
|--------------|------|----------|
| 実支払レコード | 実際の支払い行為の記録 | 必須属性として意味を持つ |
| 買い物集計8項目 | 買い物実績の集計値（導出データ） | **属性として適用対象外** |

同じテーブル・同じ集約に入れているため、集計レコードにも支払方法という属性が強制されている。その結果、NULL の意味が「未設定」と「適用対象外」の2種類生まれ、それを回避するために `999` という語義的にねじれた値（*支払方法を持たないこと*を*支払方法の値*で表現）が必要になった。

### 1.3 DDD観点での整理

対象8項目は「支払い行為の記録」ではなく「買い物実績の集計値」である。カラムをどうするかではなく、**集約の分離**として捉えると `999` 問題は自然に解消する。

要件定義書 7.4 の「データ作成ロジックを根本から見直す」は、この集約分離の検討を含むものとして扱うのが望ましい。

## 2. 対応方針の選択肢

要件定義書 7.4 では「NULL または別の管理方法」とされている。以下から選択する。

### 案A: 支払方法カラムをNULL許容にする

**内容**: 集計8項目のレコードは支払方法コードを NULL とし、レコード種別で必須/不要を出し分ける。

**メリット**: 影響範囲が比較的小さい。テーブル構成を変えずに済む。

**デメリット**: 「実支払レコードの入力漏れ」をDB制約で防げなくなる。同一テーブルに2種類のレコードが混在する構造自体は解消されない。**（突合レビュー指摘D5-5で追加）固定費側の`FIXED_COST_TABLE`もPAYMENT_METHOD_CODEをNULL許容にする必要があるが、集計レコード判定に必要な支出区分カラムが同テーブルに存在しない（dev1指摘W）ため、CHECK制約相当の判定条件を書きにくい。この点はdev1が`FIXED_COST_TABLE`への支出区分カラム追加を推奨した理由でもある（[支払方法固定値の設計指針](Feature1_03_dev1_支払方法固定値_設計指針.md) 4章・指摘AC）**

**整合性の担保**: CHECK制約で代替可能。

```sql
CHECK (
  (集計レコード判定 = true  AND PAYMENT_METHOD_CODE IS NULL)
  OR
  (集計レコード判定 = false AND PAYMENT_METHOD_CODE IS NOT NULL)
)
```

### 案B: 集計レコードを別テーブルに分離する

**内容**: 買い物登録から集計される8項目を、支出テーブルとは別のテーブルで管理する。

**メリット**: モデルとして最も素直。支払方法カラム自体が不要になり、NOT NULL を維持できる。訂正操作の制限も「そのテーブルに更新系UIを用意しない」だけで実現できる。

**デメリット**: 影響範囲が大きい。月別収支照会・年間収支照会の集計クエリ、`IncomeAndExpenditureRegistConfirmUseCase` の必須登録チェックなど広範囲に波及する。**（突合レビュー指摘D5-5で追加）8項目を固定費登録画面から締め出し、`FIXED_COST_TABLE`の既存8行を分離先テーブルへ移行または削除する必要がある。固定費一覧の表示件数が変わるためユーザーへの影響も生じる**

### 案C: 集計値を保持せず都度導出する

**内容**: 8項目をテーブルに永続化せず、買い物登録データから都度算出する。

**メリット**: 二重管理が消える。データ整合性の問題が原理的に発生しなくなる。

**デメリット**: 影響範囲が最大。パフォーマンス影響の検証が必要。既存の収支確定フローとの整合を取る必要がある。**（突合レビュー指摘D5-5で追加）8項目を固定費として登録する運用自体が消える。影響が最も大きく、固定費登録画面・`IncomeAndExpenditureInitUseCase`・`SimpleShoppingRegistUseCase`（既存行の加減算をやめる）まで波及する**

### 選定の観点

実装規模と得られる効果のバランスで判断する。案Aは暫定対応の延長線上にあり、案B・案Cは根本解決に近い。**要件定義書の「根本から見直す」という記述をどこまで実行するかを、設計フェーズの冒頭で決めること。**

## 3. 対応内容（要件定義書 7.4）

### 3.1 データ作成ロジックの見直し

> **【突合レビュー指摘D5-1で訂正】** 旧記述「`IncomeAndExpenditureRegistConfirmUseCase` 経由で集計生成される」は、dev1の要件突合レビュー指摘Aの調査で**誤りと確定した理解**である。実際の生成経路は以下の5ステップ（詳細は[ドメイン用語集](../ドメイン用語集.md)「買い物集計8項目」の節を参照）：
>
> 1. ユーザーが**固定費登録画面から固定費として登録**する（8件）
> 2. 毎月 `IncomeAndExpenditureInitUseCase.readInitInfo()` が当月分を `ExpenditureRegistItem` として展開
> 3. `IncomeAndExpenditureRegistConfirmUseCase.execRegistAction()` が `EXPENDITURE_TABLE` へINSERT
> 4. `ShoppingRegistExpenditureItemComponent` は**8項目が登録済みかをチェックするだけ**で、生成は行わない
> 5. `SimpleShoppingRegistUseCase` は既存行を取得して金額を加減算する（**行が存在しない場合はエラー**）

- 上記の生成経路（特に固定費登録画面・`FIXED_COST_TABLE`の8行）を含めて、8項目のデータ構造・生成ロジックを見直す
- 上記の案A/B/Cのどれを採るかにより作業範囲が大きく変わる。**案Bを採る場合は固定費登録画面から8項目を締め出し`FIXED_COST_TABLE`の既存8行の移行・削除設計が、案Cを採る場合は8項目を固定費として登録する運用自体の廃止（固定費登録画面・`IncomeAndExpenditureInitUseCase`・`SimpleShoppingRegistUseCase`の加減算ロジックの作り直しまで波及）が必須になる**

### 3.2 「支払方法がない」固定値の削除

dev1で作り込んだ以下を削除・修正する。dev1設計メモの「dev5への引き継ぎ事項」（[支払方法固定値の設計指針](Feature1_03_dev1_支払方法固定値_設計指針.md) 4章）と対応。

- [ ] 支払方法マスタからシステム予約行 `999` を削除
- [ ] `PaymentMethodCode#isSystemReserved()` の参照箇所（判定自体を残すかは予約帯の他用途次第）
- [ ] `findSelectableByUserId()` と `findByUserId()`（予約値がなくなれば統合可能）
- [ ] **`findEnabledByUserId()` / `PaymentMethodInfoComponent.getFixedCostPaymentMethodOptions()`（突合レビュー指摘D5-3で追加。固定費登録画面専用に新設したメソッド。予約値がなくなれば`findSelectableByUserId()`と統合可能）**
- [ ] ユーザー入力経路の `999` 弾きバリデーション
- [ ] **`FixedCostInfoUpdateForm.isPaymentMethodCodeValid()` の条件付きバリデーション（突合レビュー指摘D5-3で追加。一律拒否ではなく「8項目のときのみ`999`を許容する」ロジックのため、上記の「弾きバリデーション」とは別項目として扱う）**
- [ ] 表示変換 `999 → －`（案Aを採る場合、NULL → `－` に変更）
- [ ] 既存データの逆変換（`999` を NULL または新構造へ）
- [ ] **`PAYMENT_METHOD_TABLE.ENABLE_UPDATE_FLG`カラム・`PaymentMethod.enableUpdateFlg`フィールドの要否判断（突合レビュー指摘D5-6。dev1設計指針4章・指摘Jで追加された引き継ぎ事項）**

**実行順序（突合レビュー指摘D5-2で訂正）**：`EXPENDITURE_TABLE` の UPDATE → **`FIXED_COST_TABLE` の UPDATE** → マスタからの DELETE。逆順ではFK制約違反になる。dev1で `PAYMENT_METHOD_CODE` を追加した3テーブルのうち`FIXED_COST_TABLE`にも対象8項目に対応する固定費8行に`999`が入っている（dev1設計書6.1節ステップ3・指摘T）ため、旧記述「支出データのUPDATE→マスタからのDELETE」のままでは`FIXED_COST_TABLE`側の`999`参照が残りFK制約違反になる。`FIXED_COST_TABLE`側の対象行の特定は、dev1移行スクリプト（設計書6.1節ステップ3）と同じ手順（候補抽出→目視確認→`FIXED_COST_CODE`明示列挙）を用いる。なお案Bまたは案Cを採る場合、`FIXED_COST_TABLE`の8行は`999`を別値に付け替えるのではなく**行そのものを削除・移行する**ことになる可能性が高いが、その場合も「支払方法マスタのDELETEより先に処理する」という順序制約は同じ。

### 3.3 訂正操作の制限

収支登録画面から対象8項目の金額をユーザーが直接変更・削除できないよう制限する。

- 判定には dev1 で作成した `ShoppingAggregateSpecification`（支出項目コード＋無駄遣い区分）を再利用する
- 画面上のボタン非活性化だけでなく、**サーバー側でも更新リクエストを弾くこと**
- 案Bを採用した場合は、テーブル分離により構造的に制限される

## 4. 設計フェーズで検討すべき事項

### 4.1 影響範囲の洗い出し（持ち越し事項No.6）

`IncomeAndExpenditureRegistConfirmUseCase` のどの処理をどう変更するかを確定し、実装規模を見積もる。以下の参照元を確認すること。

- `ShoppingRegistExpenditureItemComponent`（必須登録チェック）
- 月別収支照会（支出別タブ・支出項目別タブ）
- 年間収支照会（まとめ・明細）
- `SISYUTU_KINGAKU_TABLE` / `INCOME_AND_EXPENDITURE_TABLE` への集計反映
- dev2 のクレカポイント減算による遡及更新ロジック（対象レコードの判定と競合しないか）
- **固定費登録画面**（`FixedCostInfoUpdateForm` / `FixedCostRegistConfirmUseCase` / `FixedCostInquiryUseCase`）（突合レビュー指摘D5-4で追加）── 8項目を固定費として登録するUI。案B・案Cを採ると、ここから8項目を締め出す設計が必要
- **`IncomeAndExpenditureInitUseCase.readInitInfo()`**（突合レビュー指摘D5-4で追加）── 固定費→収支の展開処理。8項目の行がここで生成される
- **`FIXED_COST_TABLE`**（突合レビュー指摘D5-4で追加）── 8項目に対応する固定費8行そのものの扱い
- **`SimpleShoppingRegistUseCase`**（突合レビュー指摘D5-4で追加）── 既存のこれらの行を取得して金額を加減算する形で更新している（行が存在しない場合はエラー）。案Cで行を持たなくする場合、この加減算ロジックごと作り直しになる。`ShoppingRegistExpenditureItemComponent`（必須登録チェックのみ）とは別クラスである点に注意

### 4.2 無駄遣い区分の持ち方（発展課題）

現状、無駄遣い区分（通常／軽度／重度）は**支出テーブル側の属性**になっている。しかし食費の無駄遣い度合いは本来「支出項目の分類」であり、個々の支出レコードの属性としてはやや不自然。

- この構造のため、集計8項目の判定が「支出項目コード＋無駄遣い区分」の複合条件になっている
- 支出項目マスタ側の属性にできれば、判定が単純化され、マスタ側にフラグを持たせる案も採れる

ただし影響範囲は買い物登録・集計ロジック全体に及ぶため、**本devのスコープに含めるかは慎重に判断すること**。集約分離（案B/C）を採る場合は同時に整理できる可能性がある。

> **【突合レビュー指摘D5-7で追加】** [支払方法固定値の設計指針](Feature1_03_dev1_支払方法固定値_設計指針.md) 4章（指摘AC）は、同じ課題への別の解決策として「`FIXED_COST_TABLE`に支出区分の専用カラムを追加する」を挙げている。**この2つは競合するのではなく、本節（無駄遣い区分を支出項目マスタ側の属性にする）の方が上位互換の解決策**である。本節が実現すれば支出区分は支出項目コードから一意に決まるため、`FIXED_COST_TABLE`に専用カラムを持つ必要がなくなり、`ExpenditureCategory.from(FixedCostName)`の文字列マッチ依存（dev1指摘W・AC。5.4.1節のバリデーションと移行スクリプトの2箇所が依存）も同時に解消される。8項目の判定も「支出項目コード単体」で済むようになり、`ShoppingAggregateSpecification`が単純化される。**本devのスコープ判断時には、dev1が積み残した文字列マッチ依存2箇所の解消というメリットも計上すること。**

# 設計インプット：支払方法種別に「電子マネー（前払い式）」を追加する

本ドキュメントは Claude Code への作業インプットです。
**「決定事項」は議論済みの確定事項として扱い、再検討や代替案の提示は不要**です。
「実装指示」に従って設計・実装を進めてください。不明点があれば実装前に質問してください。

---

## 1. 背景

現行の家計簿アプリでは、支払方法種別として以下の 4 つを定義している。

| コード | 種別 |
|---|---|
| 1 | 現金 |
| 2 | 口座振替 |
| 3 | クレジットカード |
| 4 | デビットカード |

近年 PayPay・イオン電子マネー等のキャッシュレス決済（前払い式電子マネー）の利用が増えたため、
その扱いを整理した結果、以下の方針で対応することにした。

---

## 2. 決定事項（確定・再検討不要）

### 2.1 チャージ残高は管理しない

- 電子マネーへのチャージ金額は **登録しない**。
- 電子マネーの残高が現在いくらあるかも **管理しない**。
- 支出として登録するのは **購入した商品・サービスのみ**（購入時点で費目別に計上する）。

**根拠**：チャージは「現金・預金が前払い残高へ移動しただけ」であり、支出そのものではない。
チャージと購入の両方を支出計上すると二重計上になる。市販の家計簿アプリ（Zaim、マネーフォワード ME 等）
も、チャージ側を「振替」または「集計対象外」として扱い、購入時点のみを支出計上する設計を採っている。
総務省家計調査の記入要領でも、チャージ時点は「電子マネーの利用」に含めない扱いとなっている。

### 2.2 カード連携払いはクレジットカードとして登録する

- PayPay のクレジットカード払いなど、**カードに紐づけて決済した場合は実質クレジットカード払い**であるため、
  支払方法種別 `3:クレジットカード` として登録する。
- 電子マネー種別として登録するのは **残高から支払った場合のみ**。

### 2.3 支払方法種別に「電子マネー（前払い式）」を追加する

- 残高管理をしないことと、支払方法種別を持つかどうかは **独立した論点**である。
- 残高を追わなくても、種別として持たなければ「キャッシュレスで月いくら使ったか」を集計できず、
  過去データの遡及修正も効かない。
- したがって **種別のみ追加し、チャージ・残高管理機能は今回スコープ外**とする。

---

## 3. 今回のスコープ

### やること

- 支払方法種別に前払い式電子マネーを表す値を 1 つ追加する。
- 追加に伴い、種別ごとの不変条件（引落口座の要否）を整理し、判定ロジックを一箇所に集約する。
- 種別の判別基準を用語集・要件定義に明文化する。

### やらないこと（明示的に対象外）

- チャージ金額の登録機能
- 電子マネー残高の保持・整合性チェック
- 資産アカウント／資金移動（振替）の概念導入
- 後払い型電子マネー（PayPay あと払い等）を独立した種別として扱うこと
  → 現時点では `3:クレジットカード` に含める

---

## 4. 実装指示

### 4.1 種別値の追加

- コード値 `5` を追加する。
- **enum 名には「前払い式」であることを残すこと**。例：`PREPAID_EMONEY` / `PREPAID_ELECTRONIC_MONEY`。
  - 単なる `ELECTRONIC_MONEY` は不可。将来 後払い型を独立させたくなった際に意味が曖昧になるため。
- 表示名（日本語ラベル）は「電子マネー（前払い式）」など、前払いであることが利用者に伝わる文言とする。
- 実際のクラス名・命名規約は既存コードベースの流儀に合わせること。

### 4.2 引落口座の要否を種別の責務として持たせる

種別ごとに引落口座の紐付け要否が異なる。

| コード | 種別 | 引落口座 |
|---|---|---|
| 1 | 現金 | 不要 |
| 2 | 口座振替 | 必須 |
| 3 | クレジットカード | 必須 |
| 4 | デビットカード | 必須 |
| 5 | 電子マネー（前払い式） | **不要** |

**実装上の注意**：既存のバリデーションが「現金だけが例外」という書き方（`if (種別 == 現金)` 等）に
なっている場合、種別追加時に条件分岐の追加漏れが発生する。

これを防ぐため、**種別 enum 自身に `requiresAccount()` のような述語を持たせ、
呼び出し側は述語を参照するだけにする**こと。既存の分岐箇所を洗い出し、すべて述語呼び出しに置き換える。

```
// NG（種別追加のたびに修正が必要・漏れやすい）
if (type == CASH) { ... }

// OK（判定ロジックが enum に集約される）
if (type.requiresAccount()) { ... }
```

### 4.3 運用ルールの明文化

以下の判別基準を、要件定義書またはドメイン用語集に記載すること。
コード上には現れないが、データの一貫性を左右するルールである。

> **電子マネー決済時の支払方法種別の判別基準**
>
> 決済時にアプリ側でどの支払元を選択したかを基準とする。
> - 残高から支払った場合 → `5:電子マネー（前払い式）`
> - 紐づけたクレジットカードから支払った場合 → `3:クレジットカード`
>
> なお、チャージ金額および電子マネー残高は本アプリの管理対象外とする。
> 支出として登録するのは購入した商品・サービスのみ。

---

## 5. 将来拡張の方針（今回は実装しない）

残高管理を後から導入する場合、**支払方法種別の enum に残高属性を追加するのではなく、
資産アカウントを独立した集約として切り出す**方針とする。
チャージは「支出」ではなく「資産アカウント間の資金移動」としてモデリングする。

今回の変更を種別追加に留めておけば、この拡張は既存モデルを壊さずに追加できる。
**この方針に反する設計（種別に残高フィールドを持たせる等）は採用しないこと。**

# dev1 設計指針: 支払方法マスタのシステム予約値の扱い

**対象**: `feature-1.03-dev1`
**位置づけ**: 要件定義書 3.1「支払方法がない固定値」および 3.3「支払方法に紐づかない支出データの扱い」の設計方針を補足するもの
**作成経緯**: 支払方法カラムに「ユーザー選択値」と「システム固定値」が混在する設計の是非を検討した結果をまとめたもの

---

## 1. 前提となる設計判断

### 1.1 なぜシステム予約値を使うのか

買い物登録から集計される支出8項目（要件定義書 3.3 / 7.3）は複数の支払方法の合算値であり、単一の支払方法に紐づけられない。この「支払方法という属性が適用対象外」という状態を表現する方法として、以下を検討した。

| 案 | 内容 | 判断 |
|----|------|------|
| A | 支払方法マスタにシステム予約行を追加 | **採用** |
| B | カラムをNULL許容にし、レコード種別で出し分け | 不採用 |
| C | 集計レコードを別テーブル/導出値に分離 | dev5で検討 |

**採用理由**: ユーザーにとって支払方法は必須入力項目であり、テーブル定義上 NOT NULL 制約を維持したいため。

**留意点**: 本来「該当なし」を表すためだけのマスタ行は NULL の代用であり、設計としては望ましくない。dev5で削除する前提の暫定対応であることを明確にしておく。

### 1.2 dev5での削除が前提

本対応は暫定措置である。dev5で以下を実施する予定のため、**削除しやすい実装にすること**を最優先の設計方針とする。

- システム予約値の削除
- 対象8項目のデータ作成ロジックの根本見直し
- 対象8項目に対するユーザーの訂正・削除操作の制限

---

## 2. 実装方針

### 2.1 コード体系

- **予約帯**: `990`〜`999` をシステム予約とする（既存の店舗マスタ管理と同一ルール）
- **「支払方法がない」**: `999`
- 桁数・ゼロ埋め有無は既存の支払方法コード採番規則に合わせること

### 2.2 定数の一元管理

`999` をコード中に直書きしない。値オブジェクトまたは定数クラス1箇所に定義し、判定はメソッド経由で行う。

```java
// 例
public class PaymentMethodCode {
    private static final String NOT_APPLICABLE = "999";
    private static final String RESERVED_FROM   = "990";

    /** システム予約コードか判定する */
    public boolean isSystemReserved() { ... }
}
```

**理由**: dev5の削除時に、この判定を参照している箇所を辿るだけで影響範囲が特定できるようにするため。

### 2.3 リポジトリ層での除外

画面の選択肢にシステム予約値が出ないよう、**取得メソッド自体を分ける**。UseCase側で個別に `if` による除外を書かない。

| メソッド | 用途 | 予約値 |
|----------|------|--------|
| `findByUserId()` | 表示・JOIN用（全件） | 含む |
| `findSelectableByUserId()` | 画面のプルダウン用 | **除外** |

**対象画面**（`findSelectableByUserId()` を使う箇所）:

- ~~固定費登録~~ **【例外】固定費登録は対象外**（下記参照）
- 収支登録
- 買い物登録（簡易タイプ含む）
- 店舗マスタ管理（デフォルト支払方法の選択）
- 支払方法マスタ管理（一覧表示では予約行を編集不可にする）
- dev4 買い物照会のフィルタ条件
- dev2 支払い確認画面のクレジットカード選択

**理由**: 除外条件を各UseCaseに散らすと、1箇所の漏れがそのままバグになる。

> **【dev1設計時の例外・突合レビュー指摘X】固定費登録画面のみ`findSelectableByUserId()`を使わない**：dev1設計フェーズでの調査により、買い物集計8項目（要件3.3・7.3）は固定費として登録し「固定費→収支登録」の引き継ぎ機能でEXPENDITURE_TABLEへ伝播する運用であることが判明した（dev1設計書 突合レビュー指摘A）。そのため固定費登録画面では「支払方法がない」を選択できる必要があり、代わりに`findEnabledByUserId()`（ENABLE_FLG=trueのみで絞り込み、システム予約値は除外しない）を使う。詳細はdev1設計書5.4.1節を参照。

### 2.4 サーバー側バリデーション

NOT NULL かつマスタに実在する値になるため、**リクエストを改変すれば `999` を送信できてしまう**。DB制約・FK制約では防げないため、アプリケーション層で明示的に弾く。

- ユーザー入力経路（~~固定費登録~~・収支登録・買い物登録）では、支払方法コードがシステム予約帯の場合はバリデーションエラーとする
- `PaymentMethodCode#isSystemReserved()` を使って判定する
- **【dev1設計時の例外・突合レビュー指摘X】固定費登録は上記の一律拒否対象から除く**。ただし無条件に許容するわけではなく、支払方法コードがシステム予約値の場合は「その固定費の支出項目コード・支出区分（固定費名から導出）が買い物集計8項目に一致するときのみ許容し、一致しない場合はバリデーションエラーとする」条件付きバリデーションを設ける（dev1設計書5.4.1節・突合レビュー指摘V参照）。

### 2.5 表示

- 支払方法コードが `999` の場合、画面表示は `－` とする
- **変換ロジックは1箇所に集約する**。Thymeleaf側や各画面のViewに分散させない

**対象箇所**:

- 月別収支照会（支出別タブ）の「支払方法」列
- dev4 買い物照会一覧の「支払方法」列
- 将来的なCSV出力等

**マスタ上の名称**: 画面には `－` として表示されるため、マスタメンテナンス画面で用途が分かる文言（例: `(システム予約) 支払方法なし`）にしておくと保守しやすい。

### 2.6 対象8項目の判定ロジック

対象8項目の判定は **支出項目コード ＋ 無駄遣い区分（通常／軽度／重度）の組み合わせ** で行う。

- 支出項目コードは全ユーザー共通のシステム予約コードであるため、Java側の定数として保持して問題ない
- 同一支出項目コードの重複登録はシステム上禁止されている（一意性が担保されている）
- 無駄遣い区分は支出テーブル側の属性であるため、支出項目コード単体では判定できない

**実装方針**: 判定を Specification として独立させ、8組の定義を1箇所に列挙する。

```java
// 例
public class ShoppingAggregateSpecification {

    private static final Set<ItemKey> TARGETS = Set.of(
        // 要件定義書 7.3 の8項目と1対1で対応させる
        // 食費(無駄遣いなし) / 食費(無駄遣いB) / 食費(無駄遣いC)
        // 日用消耗品 / 衣類・クリーニング・靴 / 住居設備 / 外食 / 仕事(流動経費)
    );

    public boolean isSatisfiedBy(/* 支出レコード */) { ... }
}
```

**理由**: dev5では「データ作成ロジックの見直し」と「訂正操作の制限」の両方から同じ判定が必要になる。1箇所にまとめておくことで判定基準のズレを防ぎ、dev5の作業範囲を明確にできる。

> **【文字列依存は存在しないことを確認済み・突合レビュー指摘S2】** 本節は当初「現状の識別が項目名の `【更新不可予定額(アプリ更新)】` という文字列に依存している**場合は**、この Specification に置き換えること」という条件付きの指示だったが、**dev1着手前のソースを `アプリ更新` / `更新不可予定額` でgrepした結果、いずれの文字列もコード中に存在しないことが確認された**（ユーザー確認済み）。したがって置き換え作業は発生せず、本 Specification は最初から `(支出項目コード, 支出区分)` のみで判定する。dev5でこの記述を読んだ際に「未着手の置き換え作業が残っている」と誤解しないこと。
>
> `【更新不可予定額(アプリ更新)】` は、ユーザーが固定費を登録する際の**命名規約**（この固定費の予定額はアプリが自動更新するため手動更新しない、という運用上の目印）であり、`FIXED_COST_NAME` に含まれ、収支登録処理で `EXPENDITURE_NAME` に引き継がれる。`SISYUTU_ITEM_NAME` は `VARCHAR(15)` であり16文字の当該文字列は格納できないため、支出項目名に付いているという理解は誤りである（dev1設計書6.1節に実データ例あり）。
>
> **区別すべき点**：文字列依存が存在しないのは `【更新不可予定額(アプリ更新)】` についてのみである。支出区分の導出に使う `無駄遣いB` / `無駄遣いC`（`ExpenditureCategory.from(FixedCostName)`）への依存は実在し、dev1でも利用している（指摘W・AC。4章のdev5引き継ぎ事項を参照）。文字列マッチが壊れやすいという原則自体は変わらないため、後者の解消はdev5の課題として残る。

## 3. 既存データ変換時の注意（要件定義書 3.4）

- **実行順序**: 支払方法マスタへのシステム予約行 INSERT → 支出・収支・**固定費**データの UPDATE の順で行う。逆順ではFK制約違反になる（**4次確認レビュー指摘AI-2で指摘・dev5設計指針との突合レビュー指摘D5-9で修正**。dev1設計書6.1節ステップ1は指摘Tを受けて「支出・収支・固定費データ」に更新済みだが、本節が未追随だった）
- 対象8項目への `999` 設定には、2.6 の判定条件（支出項目コード＋無駄遣い区分）と同じ条件を使うこと
- 変換スクリプトはベースラインとして保存し、dev5で逆変換を書く際の参照元にする

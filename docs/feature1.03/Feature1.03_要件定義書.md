## 1. 概要

Feature1.03として、以下の機能を家計簿に取り込む。

### 1.1 必須ゴール

| No | 機能 | 概要 |
|----|------|------|
| ① | 支払方法登録 | 現金・口座振替・クレジットカード・デビットカードなどの支払方法を、固定費登録・収支登録・買い物登録で選択できるようにする |
| ② | クレジットカードポイント減算 | 翌月引落のクレジットカード利用代金のうち、指定店舗の利用代金からポイント利用分を減算できるようにする |

### 1.2 追加で取り込む機能（実現可能なら対応）

| No | 機能 | 概要 |
|----|------|------|
| ③ | 積立金残高管理 | 支出として登録している積立金と、収入として登録する積立金取崩額を紐づけし、積立金の種類ごとの残高を確認できるようにする |
| ④ | 店舗・支払方法別買い物照会 | 指定した店舗・支払方法・集計期間で買い物明細を絞り込み、利用代金合計を照会できるようにする。クレジットカードの場合は支払方法マスタの集計開始日から集計期間を自動算出する |
| ⑤ | 支出8項目のデータ管理見直し・操作制限 | 買い物登録から集計される支出8項目のデータ作成ロジックを見直し、「支払方法がない」固定値を削除する。あわせてユーザーによる直接編集・削除を制限する |

## 2. フェーズ構成と依存関係

```
feature-1.03-dev1: ①支払方法マスタ・銀行口座マスタ + 3画面への支払方法追加
feature-1.03-dev2: ②クレカポイント減算 + 口座別支払確認画面（dev1完了が前提）
feature-1.03-dev3: ③積立金残高管理（dev1・dev2と独立して進行可能）
feature-1.03-dev4: ④店舗・支払方法別買い物照会（dev1完了が前提。dev2・dev3より後を推奨）
feature-1.03-dev5: ⑤支出8項目のデータ管理見直し・操作制限（dev1完了が前提。dev4完了後を推奨）
```

- dev2はdev1で登録した支払方法（特にクレジットカード種別・集計期間・銀行口座紐づけ）のデータを前提とするため、**dev1完了後に着手**する。
- dev3は支払方法と直接の依存関係がないため、dev1・dev2と並行 または 後続で進行可能。
- dev4はdev1で登録した支払方法マスタ（集計開始日）を利用するため、**dev1完了後に着手**する。dev2・dev3とは独立して進行可能（ただし実装順はdev3より後を推奨）。
- dev5はdev1で設定した「支払方法がない」固定値の後始末のため、**dev1完了後に着手**する。dev4完了後に実施することを推奨する。

### 進め方の方針

- **要件定義**: dev1〜dev5をまとめて実施（本書はこの工程の成果物）
- **紙芝居（画面モックアップ）**: dev1〜dev4の画面をまとめて作成し、画面構成・タブ遷移・表示項目の一貫性を確認する（dev5は画面変更なし）
- **設計・実装・テスト**: dev1 → dev2 → dev3 → dev4 → dev5 の順に逐次実施する

## 3. dev1: 支払方法・銀行口座管理

### 3.1 マスタ管理画面（新規・拡張）

#### 銀行口座マスタ管理（新規）
- ユーザーごとに銀行口座を登録・編集できる
- 管理項目: 銀行口座コード、銀行名、口座メモ（口座のエイリアス）、**表示順**、有効/無効フラグ
- **削除は実装しない**。店舗マスタ（`ShopInfoManageUseCase`）と同様、他テーブル（支払方法マスタ）から参照される基準データであるため、物理削除は行わず、使わなくなった口座は無効フラグで**固定費登録・収支登録・買い物登録など各登録画面の選択肢（プルダウン）に表示しない**・選択不可にする方式とする。**銀行口座マスタ管理画面自体の一覧には、再有効化できるよう無効状態がわかる形で表示を残す**（要件突合レビュー指摘O対応。当初「一覧から非表示」としていたが、これは各登録画面の選択肢を指す記述であり、マスタ管理画面自体の一覧から完全に消す仕様ではなかったため訂正した）
- **表示順**: 店舗マスタ（`SHOP_SORT`）と同じUI・運用パターン。登録時に表示順を入力し、一覧はその順でソート表示する。支払方法マスタの銀行口座選択でも参照されるため、よく使う口座を上位に表示できるようにする

#### 支払方法マスタ管理（新規）
- ユーザーごとに支払方法を登録・編集できる（ユーザーが使用している銀行・クレジットカードを自由に登録）
- 管理項目:
  - 支払方法コード
  - 支払方法名（例: 楽天カード、PayPay銀行 口座振替）
  - 支払方法種別: 現金 / 口座振替 / クレジットカード / デビットカード / **電子マネー（前払い式）**
  - 銀行口座（**種別により要否が異なる**。下表参照）
  - 集計開始日（クレジットカードのみ）: 1〜28の日付（29〜31日はうるう年・月末日数の考慮が煩雑になる一方、実在のクレジットカードで29〜31日を集計開始日とするものはないため対象外とする）。集計期間は「開始日 〜 翌月（開始日の前日）」として算出する（例: 開始日=1 → 1日〜月末、開始日=15 → 15日〜翌月14日）
  - **表示順**
  - 有効/無効フラグ

  | 支払方法種別 | 銀行口座 |
  |------------|---------|
  | 現金 | 不要 |
  | 口座振替 | 必須 |
  | クレジットカード | 必須 |
  | デビットカード | 必須 |
  | 電子マネー（前払い式） | 不要 |

- **電子マネー（前払い式）の扱い**（PayPay残高払い・イオン電子マネー等のキャッシュレス決済を想定）
  - チャージ金額・電子マネー残高は本アプリの管理対象外とする。支出として登録するのは購入した商品・サービスのみとし、チャージ自体は支出計上しない（チャージと購入の両方を計上すると二重計上になるため）
  - **判別基準**：決済時にアプリ側でどの支払元を選択したかを基準とする
    - 残高から支払った場合 → 支払方法種別「電子マネー（前払い式）」として登録
    - 紐づけたクレジットカードから支払った場合 → 実質クレジットカード払いのため、支払方法種別「クレジットカード」として登録する（電子マネー種別としては登録しない）
  - 後払い型電子マネー（PayPayあと払い等）も現時点では独立種別とせず、「クレジットカード」種別に含めて登録する（残高を持たずカードと同様の月次精算のため）
  - 将来的に電子マネーの残高管理を導入する場合は、支払方法種別に残高属性を追加するのではなく、資産アカウント（資金移動の概念）を独立した集約として切り出す方針とする
- **削除は実装しない**。銀行口座マスタと同様の理由（固定費・収支・買い物の各テーブルから参照されるため）で、無効フラグによる**各登録画面の選択肢（プルダウン）への非表示**・選択不可方式とする。**支払方法マスタ管理画面自体の一覧には、再有効化できるよう無効状態がわかる形で表示を残す**（銀行口座マスタと同じ方針。要件突合レビュー指摘O対応）
- **表示順**: 店舗マスタと同じUI・運用パターン。固定費登録・収支登録・買い物登録で毎回選択操作が発生するため、よく使う支払方法を上位に表示できるようにする
- **「支払方法がない」固定値**: 買い物登録から集計される支出8項目（後述）用に、システム固定の「支払方法がない」エントリをマスタに保持する。店舗マスタの変更不可システム行と同様に、ユーザーからは編集・削除不可とする。dev5で当該8項目の根本的なデータ管理方法を見直した際に削除予定

用語の詳細（電子マネー・システム予約値など）は [ドメイン用語集](../ドメイン用語集.md) を参照。

#### 店舗マスタへのデフォルト支払方法追加（既存画面の拡張）
- 既存の店舗マスタ管理画面（`ShopInfoManageUseCase`）に、**デフォルト支払方法（任意）** フィールドを追加する
- DB変更: `SHOP_TABLE` に `DEFAULT_PAYMENT_METHOD_CODE` カラムを追加する（NULL許容）
- 店舗登録・編集時に、その店舗でよく使う支払方法を事前に設定できる。**任意項目**のため「設定しない」選択も可
- **一覧表示**: 店舗一覧テーブルに「デフォルト支払方法」列を追加する
- **買い物登録との連携**: 買い物登録（簡易タイプ含む）で店舗を選択した際、その店舗にデフォルト支払方法が設定されている場合は支払方法選択の初期値として自動設定する

### 3.2 既存登録画面への支払方法追加

| 画面 | 内容 |
|------|------|
| 固定費登録 | 支払方法の選択を追加（**必須**） |
| 収支登録 | 支払方法の選択を追加（**必須**）。固定費から収支を生成するタイミング（初期登録時）では、固定費に登録されている支払方法を引き継ぐ |
| 買い物登録 | 支払方法の選択を追加（**必須**）。店舗選択時、選択した店舗にデフォルト支払方法が設定されている場合は支払方法の初期値として自動設定する（3.1参照） |

`AccountMonth.html` の支出別タブに「支払方法」「引落先口座」列を追加する。

| 現行 | 変更後 |
|------|--------|
| 支出名(区分) / 支払日 / 支出金額 / 訂正 / 詳細 | 支出名(区分) / **支払方法** / 支払日 / 支出金額 / **引落先口座** / 訂正 / 詳細 |

#### 支払方法に紐づかない支出データの扱い

買い物登録から日々集計される以下の8項目（`IncomeAndExpenditureRegistConfirmUseCase` の必須登録チェック `ShoppingRegistExpenditureItemComponent` が対象とする集計専用レコード）は、複数の支払方法（現金・クレカ・デビットカード等）の合算値であり、単一の支払方法に紐づけられない。

**対象8項目**: 食費(無駄遣いなし／無駄遣いB／無駄遣いC)、日用消耗品、衣類・クリーニング・靴、住居設備、外食、仕事(流動経費)。**判定は支出項目コード＋支出区分（無駄遣い区分）の組み合わせで行う**（項目名に「【更新不可予定額(アプリ更新)】」が付くもの、という文字列ベースの説明は実装（`ShoppingRegistExpenditureItemComponent`）と一致しないため、要件突合レビュー指摘R-2により組み合わせベースの記述に修正した）。この8項目は、ユーザーが固定費登録画面から固定費として登録しておく運用であり、毎月「固定費→収支登録」の引き継ぎ機能によりEXPENDITURE_TABLEへ反映される（dev1設計時の確認により判明。要件突合レビュー指摘A）。

- **dev1〜dev4での対応**: 支払方法マスタの固定値「支払方法がない」を設定する。訂正操作の制限は行わない（ユーザーの運用で対応）。**ただし技術的な理由（後述）により、支払方法欄のみdev1で入力補助上の制御が入る**：支払方法プルダウンの選択肢には予約値「支払方法がない」を表示しない方針としたため（固定費登録画面を除く）、現在値が「支払方法がない」である行を収支登録画面の訂正フォームで開いた場合に限り、支払方法欄をdisabled表示にして値を維持する。これは「訂正操作の制限」（主に金額の訂正を指す）には当たらない技術的な安全策であり、金額欄・他の項目の訂正には一切影響しない（dev1設計書5.5節、要件突合レビュー指摘Q対応）。
- **既存DBデータの変換**: 上記8項目に対応する既存の支出・収支データには、変換スクリプトにて「支払方法がない」値を一括設定する
- **dev5での対応予定**: これらの項目のデータ作成方法を根本的に見直し、「支払方法がない」固定値を削除する。また、ユーザーによる金額の直接更新不可（訂正操作制限）についても同タイミングで対応する

### 3.4 既存データへの支払方法設定

すでに登録済みの固定費・収支・買い物データには支払方法が設定されていないため、変換が必要。

- **方針**: SQLスクリプトをベースラインとして作成する
  - 簡単なルールに一致するデータは自動設定（例: 家賃→指定の口座振替、特定店舗→現金）
  - ルールに一致しないデータは「現金」をデフォルト設定
  - ルール不一致で手修正が必要なデータは手作業で確認・修正する
- **規模次第での発展**: 手修正対象の件数を確認した上で、件数が多い場合はバッチ処理またはAdmin画面（既存データ変換機能）への発展を検討する（~~設計フェーズで件数を確認し判断~~ **→ dev1設計時に判断タイミングを見直し、製造・テスト完了後、本番適用前に本番DBを確認してから判断することとした**（dev1設計書「設計上の確認事項④」参照。要件突合レビュー指摘P対応））

## 4. dev2: クレジットカードポイント減算・口座別支払確認

### 4.1 前提条件

dev1の支払方法・銀行口座データが存在すること。

### 4.2 クレジットカードポイント減算

#### タイムライン

```
利用月(M)        → 引落月(M+1)     → ポイント確定月(M+2以降)
店舗Xで5,000円利用 → 5,000円引落      → 300円ポイント確定 → 登録（Mに遡及）
```

ポイント付与額は、クレカ利用月の翌々月以降に確定することがあるため、操作タイミングは「ポイント確定後にまとめて登録」とする。

#### 対象範囲

- **対象**: `SimpleShoppingRegistUseCase`（買い物登録）で登録された、クレジットカード支払いの買い物のみ
- **対象外**: 固定費由来の支出（`IncomeAndExpenditureRegistConfirmUseCase` 経由で登録された支出。固定費がクレジットカード払いであっても対象外）

#### 減算の単位

店舗単位（店舗の月間クレカ利用代金から、ユーザーが選択した支出項目に対してポイント分を減算する）

#### 登録画面の入力項目

| 項目 | 内容 |
|------|------|
| 対象クレジットカード | 支払方法マスタで種別=クレジットカードのものから選択 |
| 適用月 | 元の利用月(M)。遡及修正の対象月 |
| 店舗 | 店舗マスタから選択 |
| 支出項目 | ユーザーが選択（**(a)案**: 比例按分や店舗別自動判定は行わない） |
| ポイント金額 | 正の値のみ |
| メモ | 任意 |

#### データ更新方針（マイナス支出は登録不可のため遡及更新で対応）

新規テーブル `CREDIT_POINT_DEDUCTION_TABLE` を作成し、登録時に以下4テーブルを更新する。

| テーブル | 操作 |
|------|------|
| CREDIT_POINT_DEDUCTION_TABLE（新規） | INSERT（履歴・参照用） |
| EXPENDITURE_TABLE | UPDATE（対象支出項目の金額を減算） |
| SISYUTU_KINGAKU_TABLE | UPDATE（対象支出項目の月次金額を減算） |
| INCOME_AND_EXPENDITURE_TABLE | UPDATE（月次支出合計を減算） |

※ `EXPENDITURE_TABLE` のどのレコードを減算対象とするかの判定ロジックは設計フェーズで確定する（[9. 設計フェーズへの持ち越し事項](#9-設計フェーズへの持ち越し事項) 参照）。

#### 編集・削除

登録済みのポイント減算は編集・削除が可能（同一カードを複数店舗で利用している場合に後から金額を調整できるようにするため）。削除時は4テーブルを逆方向に更新する。

#### 表示

- **月別収支照会（支出別タブ）**: 「支出一覧」表示エリアとは別に、選択中月に登録済みのポイント減算一覧を表示する新規エリアを追加（照会のみ、入力ボタンは配置しない）。支出項目別タブでは表示しない。
- **年間収支照会（明細）**: `AccountYearMeisai.html` の明細表示エリアに、月別ポイント減算合計の列を1列追加する。

### 4.3 口座別支払確認画面

#### 画面構成

既存の `PaymentConfirmation.html`（スタブ実装済み、タブ遷移は配線済み）を実装する。

- タブ構成: 各月の収支 / 年間収支 / 支払い確認（実装対象）
- **紙芝居で確定**: クレカポイント減算UIは「支払い確認」タブ内に統合する（別タブは設けない）。対象クレジットカード選択→店舗別ポイント減算登録・一覧を同一画面に表示する
- 前月・次月のページ制御ボタン（＜ ■ YYYY年MM月度 ■ ＞）

#### 表示内容

選択中の月における、口座別の引き落とし予定額の**合計のみ**を表示する（固定費などの明細は不要）。

| 銀行名 | 口座振替 | クレジットカード | 現金＋その他 | 合計金額 |
|--------|---------|----------------|------------|---------|
| PayPay銀行 | 82,000円 | 35,000円 | 5,000円 | 122,000円 |

- 「現金＋その他」列は、現金支払いとデビットカードなど、口座振替・クレジットカード以外の支払方法の合計額
- **口座振替**: 表示対象月に該当する固定費・収支データから算出
- **クレジットカード**: 各クレジットカードの集計開始日に基づき、前回の集計期間に該当する `SHOPPING_REGIST_TABLE` のクレカ支払い合計から算出（例: 集計開始日=1のカードなら、表示対象月の前月分のクレカ利用合計）

#### 年間収支照会への反映

年間収支照会（まとめ・明細）には、口座別の引き落とし合計は表示しない（対象外）。

## 5. dev3: 積立金残高管理

### 5.1 前提条件

積立金は既に `SISYUTU_ITEM_TABLE` の階層構造（支出項目コード0033の子項目）を使い、種類別（旅行積立・車検積立など）に登録運用済み。

※運用上1件、誤って別の積立金と同じ支出項目コードで登録されていたデータがあるため、別途データ修正（支出項目コードの付け替え）を行う（本機能のスコープ外の対応）。

### 5.2 データモデル

新規テーブル `TSUMITATE_BALANCE_TABLE`（積立金残高テーブル）を作成する。

| 項目 | 内容 |
|------|------|
| USER_ID / TARGET_YEAR / TARGET_MONTH | 対象月 |
| SISYUTU_ITEM_CODE | 積立金の種類（0033配下の子コード） |
| TSUMITATE_KINGAKU | その月の積立金額 |
| TORIKUZUSHI_KINGAKU | その月の取崩金額 |
| BALANCE_KINGAKU | 残高（前月残高 + 積立 - 取崩） |

既存テーブル `INCOME_TABLE` に `SISYUTU_ITEM_CODE` を追加する。取崩（`INCOME_KUBUN=3`）登録時に「どの積立金種類への取崩か」を選択する項目を新規追加する。

### 5.3 初期データ

過去データの履歴復元は行わない。

- 導入時点（前月分）の積立金残高は、現在Excelで管理している実際の残高値を種類ごとに直接SQLでINSERTし、運用を開始する
- それ以前の月の積立金残高は照会不要（表示エリアは空でよい）

### 5.4 表示

月別収支照会の**支出項目別タブ**に、「収支」表示エリアと「支出一覧」表示エリアの間に「積立金残高」表示エリアを新規追加する。選択中月の種類別残高を表示する。データがない月は空表示でよい。

## 6. dev4: 店舗・支払方法別買い物照会

### 6.1 前提条件

dev1の支払方法マスタ（集計開始日を含む）が存在すること。

### 6.2 機能概要

買い物登録の照会系機能として、**指定した店舗・支払方法・集計期間**の利用代金を一覧・合計で表示する。  
主要ユースケースは「クレジットカードの集計期間中の特定店舗での現在の利用代金確認」であり、スマートフォンなどから手軽に確認できることを想定する。

### 6.3 フィルタ条件

| 条件 | 内容 |
|------|------|
| 店舗 | 店舗マスタから選択（省略可: 全店舗） |
| 支払方法 | 支払方法マスタから選択（省略可: 全支払方法） |
| 集計期間 | 自動算出 または 手動指定 |

**クレジットカードの集計期間自動算出**: 支払方法マスタの「集計開始日」から当月分を自動算出する。  
例: 集計開始日=15 → 前月15日〜当月14日

### 6.4 表示内容

- フィルタ条件に合致する買い物一覧。表示列はShoppingRegistInit.htmlの登録済み買い物一覧と同じ構成とする:  
  日付 / 店舗名 / 支払方法 / 食料品(必須) / 食料品B(無駄遣い) / 食料品C(お酒類) / 外食 / 日用品 / 衣料品(私服) / 仕事 / 住居設備 / クーポン金額 / 合計金額
- 合計金額の表示（一覧の最終行に合計行として表示）
- スコープ: **参照のみ**（登録・更新機能はなし）

### 6.5 表示場所

**紙芝居で確定**: 買い物照会専用の別画面（`ShoppingInquiry.html`）を新規作成する。ShoppingRegistInit.html の「支出項目」ボタン（未使用）を「買い物照会」ボタンに変更し、この画面へ遷移する。  
**理由**: 買い物登録トップ画面（ShoppingRegistInit.html）に一覧が2つになると見にくくなるため、別画面として分離する。

### 6.6 支払い確認画面からの遷移（紙芝居で追加）

`AccountBookPaymentConfirmation.html`（支払い確認タブ）の「表示」ボタン右隣に「買い物照会」ボタンを追加する。  
押下すると別タブで `ShoppingInquiry.html`（買い物照会画面）を開き、選択中のクレジットカードと集計期間をフィルタ条件として引き継いで結果を表示する。

### 6.7 モバイル確認・情報転送

本機能は「外出先のスマートフォンから現在のクレカ利用状況を確認する」ことも主要なユースケースとして想定する。

#### 選択肢と実装コスト（概算）

| 選択肢 | 概要 | 追加実装コスト | セキュリティ |
|--------|------|----------------|--------------|
| **A: モバイルブラウザで直接閲覧** | Bootstrap 5 レスポンシブ対応のため、スマートフォンのブラウザで既存画面をそのまま閲覧。レイアウト調整のみ | +2〜4時間 | 既存 Spring Security 認証のまま |
| **B: QRコード表示** | フィルタ結果の合計・期間をQRコード化して画面に表示。スマホカメラで読み取る。JS ライブラリのみ（サーバー変更なし） | +3〜6時間 | 外部サービス通信なし。QRはセッション内のみ表示 |
| **D: Web Share API** | モバイルブラウザの「共有」ボタンからOS標準の共有シート（LINEへ送る・メモ保存等）を起動。PCブラウザでは動作しない | +2〜4時間 | OS 管理。外部サービス通信なし |

> 選択肢 C（メール送信）は実装コスト（+10〜15時間、spring-boot-starter-mail設定・Gmail App Password設定など）に対して A/B/D と体験差が小さいため除外。  
> **全選択肢が無料で追加の金額コストなし。**

#### 推奨方針

**A（モバイルブラウザ直接閲覧）を前提に dev4 の画面設計を行い**、使い勝手を確認してから D（Web Share API）を +α で追加するのが最も低コスト・高セキュリティ。QRコード（B）は PC 画面を見ながらスマートフォンへ数値を転送したい場合に有効。最終的な採用方式は紙芝居・設計フェーズで決定する。

**紙芝居で確定**: A（モバイルブラウザ直接閲覧）＋D（Web Share API +α）の組み合わせに決定。照会結果エリアに「共有」ボタンを設け、OS標準の共有シートを起動する。

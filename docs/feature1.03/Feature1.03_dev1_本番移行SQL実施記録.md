# Feature1.03-dev1: 本番環境データ移行SQL実施記録

## 1. 概要

`docs/feature1.03/Feature1.03_dev1_支払方法銀行口座管理_設計書.md` の「6. データ移行設計」「8. 実装順序」15・16番で、本番適用直前に実施する計画とされていた作業（確認事項④の回答どおり）の実施記録。2026年11月に実施した。

対象ユーザーは本番環境の唯一の実ユーザー。本書では `USER_ID` を `<実際のUSER_ID>` と表記する（個人情報のため）。実際に適用する際はこの値を実際の `USER_ID` に置き換えること。

実施順序は以下の4段階（ユーザーからの依頼時の整理に準拠）。

1. テーブル定義の本番適用（DDL）
2. 本番データ移行（既存データへの `PAYMENT_METHOD_CODE` 一括設定）
3. 制約付与（`NOT NULL` 制約・外部キー制約）
4. dev1資産（アプリケーション本体）の本番デプロイ（ユーザー側で対応、本書の対象外）

各段階の前に `mysqldump` によるバックアップを取得した。

## 2. 段階1：テーブル定義の本番適用（DDL）

`schema.sql` の `CREATE TABLE IF NOT EXISTS` は既存テーブルに対しては無視されるため、既存3テーブル＋`SHOP_TABLE`へのカラム追加は明示的な `ALTER TABLE` で行う必要がある（`schema.sql` をそのまま流すと新規2テーブルだけ作られ、既存テーブルへのカラム追加が静かにスキップされる点に注意）。

```sql
-- 1. 新規2テーブル作成
CREATE TABLE IF NOT EXISTS BANK_ACCOUNT_TABLE (
    USER_ID              VARCHAR(50),
    BANK_ACCOUNT_CODE    CHAR(2),
    BANK_NAME             VARCHAR(50) NOT NULL,
    BANK_ACCOUNT_MEMO     VARCHAR(100),
    BANK_ACCOUNT_SORT     CHAR(2) NOT NULL,
    ENABLE_FLG            BOOLEAN NOT NULL,
    PRIMARY KEY(USER_ID, BANK_ACCOUNT_CODE)
);

CREATE TABLE IF NOT EXISTS PAYMENT_METHOD_TABLE (
    USER_ID                  VARCHAR(50),
    PAYMENT_METHOD_CODE      CHAR(3),
    PAYMENT_METHOD_NAME      VARCHAR(50) NOT NULL,
    PAYMENT_METHOD_MEMO      VARCHAR(400),
    PAYMENT_METHOD_KUBUN     CHAR(1) NOT NULL,
    BANK_ACCOUNT_CODE        CHAR(2),
    CLOSING_DAY              CHAR(2),
    PAYMENT_METHOD_SORT      CHAR(3) NOT NULL,
    ENABLE_FLG               BOOLEAN NOT NULL,
    ENABLE_UPDATE_FLG        BOOLEAN NOT NULL,
    PRIMARY KEY(USER_ID, PAYMENT_METHOD_CODE),
    INDEX PAYMENT_METHOD_BANK_ACCOUNT_CODE_INDEX(BANK_ACCOUNT_CODE),
    CONSTRAINT FK_PAYMENT_METHOD_BANK_ACCOUNT_CODE FOREIGN KEY(USER_ID, BANK_ACCOUNT_CODE) REFERENCES BANK_ACCOUNT_TABLE(USER_ID, BANK_ACCOUNT_CODE)
);

-- 2. 既存3テーブル＋SHOP_TABLEへのカラム追加（NULL可）
ALTER TABLE SHOP_TABLE
    ADD COLUMN DEFAULT_PAYMENT_METHOD_CODE CHAR(3) AFTER SHOP_SORT;

ALTER TABLE FIXED_COST_TABLE
    ADD COLUMN PAYMENT_METHOD_CODE CHAR(3) AFTER SHIHARAI_KINGAKU;

ALTER TABLE EXPENDITURE_TABLE
    ADD COLUMN PAYMENT_METHOD_CODE CHAR(3) AFTER EXPENDITURE_KINGAKU;

ALTER TABLE SHOPPING_REGIST_TABLE
    ADD COLUMN PAYMENT_METHOD_CODE CHAR(3) AFTER SHOPPING_REMARKS;

-- 3. SHOP_TABLEの外部キー制約
-- （DEFAULT_PAYMENT_METHOD_CODEは常にNULL可のため、データ移行を待たずこの時点で追加して問題ない）
ALTER TABLE SHOP_TABLE ADD CONSTRAINT FK_SHOP_DEFAULT_PAYMENT_METHOD_CODE
    FOREIGN KEY(USER_ID, DEFAULT_PAYMENT_METHOD_CODE) REFERENCES PAYMENT_METHOD_TABLE(USER_ID, PAYMENT_METHOD_CODE);
```

実行結果：エラーなし。

**実施時の失敗事例（教訓）**：この2件のINSERT時に、`USER_ID`の値を実際の値に置換せず、プレースホルダーの文字列（`<実際のUSER_ID>`というテキストそのもの）のまま登録してしまうミスが発生した。後続の段階3（外部キー制約の付与）で`ERROR 1452`（子テーブル行が親テーブルに存在しない）として発覚し、以下のUPDATE文で修正した。

```sql
UPDATE PAYMENT_METHOD_TABLE
SET USER_ID = '<実際の正しいUSER_ID>'
WHERE PAYMENT_METHOD_CODE IN ('001', '999');
```

診断には以下のクエリが有効だった（参照先に存在しない組み合わせを特定する）。

```sql
SELECT DISTINCT f.USER_ID, f.PAYMENT_METHOD_CODE
FROM FIXED_COST_TABLE f
LEFT JOIN PAYMENT_METHOD_TABLE p
    ON f.USER_ID = p.USER_ID AND f.PAYMENT_METHOD_CODE = p.PAYMENT_METHOD_CODE
WHERE p.PAYMENT_METHOD_CODE IS NULL;
```

## 4. 段階2：データ移行SQL

### 4.1 本番データの事前確認で判明した事実

- 対象ユーザーは1人のみ（`ACCOUNT_BOOK_USER`）
- 移行前件数：`FIXED_COST_TABLE` 47件、`EXPENDITURE_TABLE` 1647件、`SHOPPING_REGIST_TABLE` 2992件
- 買い物集計8項目（`SISYUTU_ITEM_CODE IN ('0051','0052','0050','0046','0007','0047')`）は、全期間・全月で例外なく「ちょうど8件」であることを確認済み（設計書6.1節の件数検証の前提が成立）
- `EXPENDITURE_TABLE`には、固定費名の変更（「予定額」→「確定額」等への書き換え）により、現在の`FIXED_COST_NAME`と`EXPENDITURE_NAME`が一致しない行が553件存在した。このうち大半は`SISYUTU_ITEM_CODE`では固定費マスタと対応が取れており、残りは固定費と無関係な単発の支出（旅行・冠婚葬祭・趣味等）だった

### 4.4 実施結果（確認クエリの出力）

NULL残数はいずれも0であることを確認。

| テーブル | `001`現金 | `002`口座振替(仮1) | `003`口座振替(仮2) | `004`カード(仮1) | `005`カード(仮3) | `006`カード(仮4) | `999`支払方法がない | 合計 |
|---|---|---|---|---|---|---|---|---|
| FIXED_COST_TABLE | 39 | - | - | - | - | - | 8 | 47 |
| EXPENDITURE_TABLE | 211 | 231 | 244 | 289 | 6 | 18 | 648 | 1647 |
| SHOPPING_REGIST_TABLE | 2715 | - | - | 209 | 58 | 14 | - | 2996 |

`EXPENDITURE_TABLE`の`999`=648は、買い物集計8項目×81か月（2020年3月〜2026年11月）の理論値と完全一致。`005`=6、`006`=18（ガス代・通信費・積立NISAの各6か月分）も、2026年6月〜11月の6か月分という日付分岐の理論値と一致し、移行ロジックの妥当性を確認できた。

`SHOPPING_REGIST_TABLE`の合計2996件は、事前確認時点（2992件）から4件増えているが、これは移行作業期間中の通常利用（買い物登録）による増分であることをユーザーに確認済み（移行ロジックの不整合ではない）。
